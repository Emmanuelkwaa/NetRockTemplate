# Deployment

<!-- @init:if deploy=aspire -->
Production runs on Docker Compose generated by Aspire. The AppHost (`src/backend/NetRockTemplate.AppHost/Program.cs`) is the single source of truth for development and production.

## Publish or deploy

```bash
# Write docker-compose.yaml and .env into ./aspire-output (images are not built)
aspire publish --project src/backend/NetRockTemplate.AppHost/NetRockTemplate.AppHost.csproj -o aspire-output

# Build the images and run the stack on the current Docker host
aspire deploy --project src/backend/NetRockTemplate.AppHost/NetRockTemplate.AppHost.csproj -o aspire-output
```

`aspire-output/` is git-ignored because its `.env` holds secrets. `aspire deploy` needs a value for every parameter. Pass them as environment variables (names contain dashes, so use `env`) or answer the prompts. A non-interactive run stops before starting any container and names the first missing parameter.

`aspire deploy` remembers the values in `~/.aspire/deployments/<hash>/production.json` on the deploying machine, in plain text, and reuses them next time. Protect that machine accordingly, and delete that folder to start over.

```bash
env "Parameters__jwt-secret=..." "Parameters__public-url=https://app.example.com" \
    aspire deploy --project src/backend/NetRockTemplate.AppHost/NetRockTemplate.AppHost.csproj
```

## First deployment

```bash
cp .env.example .env     # git-ignored; fill in every value
docker compose up -d --build
docker compose ps        # wait until api is healthy
```

<!-- @init:if frontend=svelte -->
The frontend listens on `HTTP_PORT` (default 3000) and proxies `/api/*` to the API on the internal network. The API is not published on the host.
<!-- @init:end -->
<!-- @init:if frontend=blazor -->
The Blazor app listens on `HTTP_PORT` (default 3000) and calls the API on the internal network (`services__api__http__0: http://api:8080`). The API is also published on `API_PORT` (default 8080), because browsers and other clients reach it directly; there is no proxy in front of it. The Blazor image is built from `src/frontend/NetRockTemplate.UI/Dockerfile` with `./src` as the build context.
<!-- @init:end -->
<!-- @init:if frontend=none -->
The API listens on `HTTP_PORT` (default 8080).
<!-- @init:end -->

Put a TLS-terminating reverse proxy in front. To join an existing proxy network such as Coolify, uncomment the `coolify` network block and the `- coolify` lines in `docker-compose.yaml`, and remove the `ports` mapping. For a quick test over plain HTTP without a proxy, set `Hosting__ForceHttps=false`.

## Configuration

Every setting is an environment variable in `.env`, listed with comments in `.env.example`. File storage is always an external S3-compatible service (`FileStorage__*`); the stack does not run MinIO.
<!-- @init:end -->

## Database migrations

The API applies EF Core migrations on startup in Development, and anywhere `Database__MigrateOnStartup=true`.

<!-- @init:if database=managed -->
Managed PostgreSQL runs in the stack with `Database__MigrateOnStartup=true`, so a fresh database is migrated on first start.
<!-- @init:else -->
Against an external database migrations do not run automatically (`Database__MigrateOnStartup=false`). Choose one:

- Apply them from a machine that can reach the database:
  ```bash
  dotnet ef database update --project src/backend/NetRockTemplate.Infrastructure --startup-project src/backend/NetRockTemplate.WebApi --connection "Host=...;Database=...;Username=...;Password=..."
  ```
- Generate an idempotent script for a DBA: `dotnet ef migrations script --idempotent -o migrate.sql` (same project arguments).
- Or set `Database__MigrateOnStartup=true` if the app's database user may change the schema.

### pg_trgm

Fuzzy search uses the `pg_trgm` extension, and the initial migration runs `CREATE EXTENSION IF NOT EXISTS pg_trgm`. On PostgreSQL 13 and later that needs the `CREATE` privilege on the database (pg_trgm is a trusted extension); older versions need a superuser. If the app's user lacks it, ask an administrator to run this once before migrating:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```

Background jobs (Hangfire) store their state in the same database, in the `hangfire` schema, which they create on first start.
<!-- @init:end -->

## Health checks

- `GET /health/live` - the process is up (used by the container healthcheck)
- `GET /health/ready` - dependencies are reachable
- `GET /health` - full report

## Keycloak (managed)

The stack runs Keycloak 26.4.7 in production mode (`start --import-realm`). It assumes a TLS-terminating reverse proxy in front: Keycloak listens on plain HTTP inside (`KC_HTTP_ENABLED`), trusts `X-Forwarded-*` headers (`KC_PROXY_HEADERS=xforwarded`) and advertises the public URL (`KC_HOSTNAME`). Do not expose its HTTP port directly to the internet.

- **Public URL**: point a hostname such as `https://auth.example.com` at Keycloak's port and set it as `KEYCLOAK_PUBLIC_URL` (own compose) or `keycloak-public-url` (Aspire). Tokens carry it as the issuer, and the API's `Authority` is `{public URL}/realms/net-rock-template`.
- **Internal calls**: the API reaches Keycloak at `http://keycloak:8080` (`Authentication__Keycloak__InternalUrl`). `KC_HOSTNAME_BACKCHANNEL_DYNAMIC=true` makes Keycloak answer those calls with internal endpoints.
- **Realm**: `keycloak/prod/realm.json` defines the realm and client with no users. The client secret (`KC_CLIENT_SECRET`), redirect URI base and web origin come from the environment. It is imported on the first start only; an existing realm is never overwritten, so changes made in the admin console survive redeploys. Create users in the admin console or connect an identity provider there.
- **Admin**: the bootstrap admin (`KEYCLOAK_ADMIN_USERNAME` / `KEYCLOAK_ADMIN_PASSWORD`) is for the master realm. Replace it with a permanent admin after the first sign-in.
- **Health**: health endpoints are on the management port (9000), which is reachable only on the compose network, never published on the host. Own compose waits for `/health/ready` before starting the API.
- **TLS required**: the API refuses to start if the public URL is `http://` (outside Development), so the stack only runs behind a TLS-terminating proxy. The internal address `http://keycloak:8080` is allowed.
<!-- @init:if database=managed -->
- **Database**: Keycloak uses its own `keycloak` database and login on the stack's PostgreSQL server. `keycloak/postgres-init/01-keycloak.sh` creates them, but PostgreSQL runs init scripts only when its data volume is empty. If the volume already exists, run the script once by hand (the postgres service already has `KEYCLOAK_DB_PASSWORD`):

  ```bash
  docker compose exec postgres bash /docker-entrypoint-initdb.d/01-keycloak.sh
  ```
<!-- @init:else -->
- **Database**: set `KC_DB_URL`, `KC_DB_USERNAME` and `KEYCLOAK_DB_PASSWORD` (Aspire: `keycloak-db-url`, `keycloak-db-username`, `keycloak-db-password`) to a database and login reserved for Keycloak, separate from the app's.
<!-- @init:end -->
<!-- @init:if deploy=aspire -->
- **Aspire**: the realm and PostgreSQL init folders are bind mounts. The generated `.env` gets their absolute paths (`KEYCLOAK_BINDMOUNT_0`, `DB_BINDMOUNT_0`), so run `aspire deploy` from a checkout on the target host, or fix those paths before `docker compose up`.
<!-- @init:end -->

## Keycloak

<!-- @init:if frontend=blazor -->
Set `Authentication__Keycloak__Authority`, `ClientId` and `ClientSecret`, and register `{API public URL}/api/auth/keycloak/callback` as a valid redirect URI (`API_PUBLIC_URL` in own compose, `api-public-url` with Aspire). See [keycloak.md](keycloak.md).
<!-- @init:else -->
Set `Authentication__Keycloak__Authority`, `ClientId` and `ClientSecret`, and register `{public URL}/api/auth/keycloak/callback` as a valid redirect URI. See [keycloak.md](keycloak.md).
<!-- @init:end -->

These are required. `docker compose up` (and `config`) stops with a message naming the missing variable, `aspire deploy` stops before starting containers, and the API itself exits at startup if any of them is empty.
<!-- @init:end -->
